> 甲方提供 **4 台** 华鲲鲲鹏服务器，用于客户现场 **联调、部署、测试与试验收**。  
> 本文 **不约定** 物理机房/机柜位置，只约定 **四台机器的角色与使用顺序**。  
> 软件名称：**机房动环管理系统**（动环监测 + 机房可视化）。  
> **对外一页说明**见同目录 `机房动环管理系统-四台服务器使用方案-简版.pdf`。

---

## 1. 四台配置概览

| 编号 | 合同资产类型 | CPU | 内存 | 存储 | 特点 |
|------|--------------|-----|------|------|------|
| **M1** | 裸金属（较轻） | 64 核 | 128 GB | ~2.4 TB | 盘小，适合边缘/采集 |
| **M2** | 云平台管理型（大） | 128 核 | 768 GB | ~38 TB | 主力业务机 |
| **M3** | 同 M2 | 128 核 | 768 GB | ~38 TB | 同 M2 |
| **M4** | 同 M2 | 128 核 | 768 GB | ~38 TB | 同 M2，大盘 |

## 2. 分工总表（推荐）

| 机器 | 主责 | 做什么 |
|------|------|--------|
| **M1** | **现场开发 + 南向采集** | 进驻甲方现场时的 **开发/编译/联调工作站**（SSH、代码仓、工具链）；兼 **采集/协议网关**、对接动环设备。**不**承担对甲方开放的 **主业务库**、**不**承担长期历史归档 |
| **M2** | **主环境 + 双机热备主节点** | 机房动环管理系统 **Web + 后端 + 主库**；甲方演示与日常访问的 **主入口**（平时浏览器指向 M2） |
| **M3** | **双机热备备节点** | 与 M2 **同版本、同国产化 OS/DB**；应用与数据库 **同步**；承担 **主备切换、故障接管** 及升级前预演；**平时不对业务用户开放** |
| **M4** | **备份 + 制品 + 恢复支撑** | 定时备份 M2/M3 库表与配置；发布包/导入包；支撑 **MTTR＜2h** 的离线恢复与压测验证 |

```text
M1（采集） ──数据──► M2（主）◄──双机热备同步──► M3（备）
                         │
                         └──备份/制品──► M4（备份仓）
```

**国产化与高可用（合同难点三）**：适配 **国产 CPU（鲲鹏）** 及测评清单内 **≥4 套 OS、≥2 套数据库**（以采购/甲方名单为准；技术栈示例：**业务库 OceanBase 类 + 历史库 TDengine 类**，名称不超出甲方名单）。

| 含义 | 说明 |
|------|------|
| **≥2 套数据库** | 平台使用 **两种** 测评库产品，分工不同（业务/配置 vs 监测历史等） |
| **双机热备** | **M2 主节点 + M3 备节点**；**每种库** 均在 M2 为 **主实例**、M3 为 **备实例**，库级 **主备同步**，与应用 VIP/切换联动 |
| **MTBF / MTTR** | 设计目标 **MTBF＞2 万小时、MTTR＜2 小时**；M4 离线备份辅助恢复 |

路径：国产架构适配（6.4.12）、库同步与切换机制、联合测试演练（6.7）。**M1/M4 不在热备对内**，M1 只写采集数据至主库入口，M4 存全库备份。

**应用与 DB 是否分机**：在 **仅四台** 前提下，**M2/M3 各部署完整栈（应用 + 业务库 + 时序库）**，形成 **对称主备**，切换简单、符合热备验收。**应用层与 DB 层物理分离** 通常需 **≥6 台**（应用主备 + 库主备）或牺牲 HA；本方案 **不采用** 仅在 M2 跑应用、M3 只跑库等非对称拆法（切换链路过长）。后续若甲方增配服务器，再评估独立 DB 集群。

## 3. 开发模式（外网 + 现场）

开发 **不只用个人电脑**，按是否在甲方现场分两种场景，**四台里的 M1 承担现场开发**：

| 场景 | 用什么 | 做什么 |
|------|--------|--------|
| **外网 / 未进驻现场** | **团队自有开发机**（笔记本、公司电脑等） | 日常编码、本地或远程 Mock 联调、打补丁包；代码通过 Git / 介质带到现场 |
| **进驻甲方现场** | **M1** + 自带笔记本（可选） | 把工程与分支带到现场；在 **M1** 上编译、改配置、接设备调试；需要时笔记本 SSH 到 M1 或仅作编辑器 |
| **给甲方看的稳定版本** | **M2** | 现场改完一版后，**部署/更新到 M2** 做演示与集成测试；避免在 M2 上长期「随手改源码」 |

说明：外网阶段用自有电脑是常态；到现场后 **用甲方提供的 M1 做开发联调** 与交付叙述一致，且不占用 M2 演示环境。

## 4. 部署 / 测试 用哪台

| 活动 | 使用机器 | 说明 |
|------|----------|------|
| 外网功能开发与代码修改 | **自有开发机** | 提交进仓库；出补丁包或指定 Git 提交号 |
| 现场功能开发与编译 | **M1** | 南向、协议、现场问题定位；编译产物部署到 M2（或 M3 试装） |
| 正式部署 / 甲方演示 | **M2** | 版本须可追溯到发布包或 Git 提交号 |
| 设备接入、协议调试 | **M1** | 采集异常优先隔离，少影响 M2 大屏与告警 |
| 功能与回归测试 | **M2** | 与演示环境一致 |
| 升级试装、破坏性测试 | **M3**（备节点） | 版本与 M2 对齐；在备机预演后再切主 |
| 双机切换 / 恢复演练 | **M2↔M3** + **M4** 备份还原 | 验证主备切换与 **MTTR**；留演练记录 |
| 性能、海量测点、备份策略验证 | **M4** | 利用大容量盘 |

## 5. 推荐使用顺序

1. **M2**：国产化 OS/DB 就绪 → 部署主节点 → 导入/初始化数据 → 集成测试通过  
2. **M3**：与 M2 **同版**部署 → 配置 **双机热备与库同步** → 主备切换演练  
3. **M1**：采集服务指向 M2（或虚拟 IP/主入口）→ Mock 逐步换真设备  
4. **M4**：备份 M2/M3 + 发布包目录 → 完成一次 **M4 备份还原** 抽检  
5. **后续发版**：远程/M1 开发 → **M3 预演** → **M2** 正式；备机同步升级

## 7. 三条纪律

1. **对外单一主入口**：浏览器与甲方演示只指向 **M2**。  
2. **版本以 M2 为准**；M3 须与 M2 **同版本且同步** 方可处于热备就绪状态。  
3. **业务入口平时仅 M2**；M3 为热备；**M1/M4 不对业务用户日常开放**。

## 8. 端口与网络、文档维护

每台机器记录：**管理 IP、业务 IP、前端端口、后端端口、采集端口、防火墙策略**。
